# Реверс-инжиниринг цепочки AVB в MT9660 mboot (8052.1.0.4)

Дата анализа: 2026-10-22. Исходник — оригинальный `RJMT9660_firmware_8052.zip`, SHA256 ZIP `bedea70fbf3f08d3c18e59d5f91e7d12828c77fac314c30fcc98332c32c88e35`. Исследование только офлайн: без перепрошивки.

## Вывод

**Загрузчик содержит настоящие функции проверки доверенного OEM AVB RSA4096-ключа**; не только текстовые строки. Эти функции имеют строгую проверку 1032-байтной длины открытого ключа и сравнивают его со встроенной копией. При несоответствии выставление `trusted=1` не происходит. Функции зарегистрированы в таблице AVB callbacks (`AvbOps`). Обнаружена вызываемая из программы автоматической загрузки U-Boot инициализация AVB через команду `avb init 0`.

**Не доказано**: выполняется ли `avb_slot_verify` при каждом штатном старте с `locked`, что делает конкретная ветка после `trusted=false`, и существуют ли нетипичные штатные режимы recovery. До этого нельзя делать вывод, что загрузчик «примет любой ключ» или что «обход невозможен принципиально».

## Доказательства

- [Статический анализ и строковые адреса](mboot_stage1.json): `mboot.img` — сырой AArch64 U-Boot; 2,658,304 байта, данные заголовка `0x400` (1024) байта. Известный SHA-256 `8819cc068a7a05243eebbc504289442e6cf24992af4562f84a4c51bdf7d691ee`.
- [Ghidra 12.1.4 анализ, граф ссылок и псевдокод](ghidra_avb.json): 3926 функций; код изображения импортирован после пропуска `0x400` байт заголовка, база адресов программы 0.
- OEM `AvbRSAPublicKey` длиной `0x408 = 1032` байта располагается по смещению оригинального файла `0x1CDAAC`, а в корректно импортированном коде Ghidra — `0x1CD6AC`. SHA256 открытого ключа `dcf38badcd7784d2aa892739eba5e239a649362edb03586a455b3f8ded046cfe`.
- Функция `0xA1AE8` (Ghidra `re_candidate_a1ae8`): проверяет, что указатели и `trusted` переданы, `param_4==0x408`; устанавливает `*trusted=0`; вызывает бинарное сравнение (`memcmp`-подобная подпрограмма `0x15ED20`) с `&DAT_001CD6AC`; только при равенстве задаёт `*trusted=1`. Также задаёт наружный флаг `*param_8=1` и возвращает статус API.
- Функция `0xA1B58`: аналогично сравнивает `0x408`-байтный полученный ключ с OEM-ключом и только при равенстве выставляет `*trusted=1`.
- Функция `0xA2628` (конструктор callback-таблицы): сохраняет адрес `0xA1B58` в таблице по смещению `+0x30`, а `0xA1AE8` по смещению `+0x88`; это согласуется с реализацией `AvbOps` (нужно уточнить структуру ABI по используемой версии libavb).
- Функция `0x50D40` выполняет команды U-Boot `checkteesuccess`, `avb init 0`, `ab slt 0`; вызывается прямой инструкцией `BL` из `0x93024`, внутри обработчика autoboot `0x92E14`.
- Отдельная функция `0x110B0` использует RSA-модуль и экспоненту из `CKB` для `DEV signature`. Её назначение не подтверждено как проверка Android vbmeta, поэтому её нельзя смешивать с основной AVB-цепочкой.
- В U-Boot также обнаружены сообщения о запрете переключения dm-verity при locked, об ошибках `vbmeta`, `anti-rollback`, и о состояниях `green`, `yellow`, `orange`.

## Чем важен статус `locked`

Работающий 8052 сообщал `ro.boot.vbmeta.device_state=locked`, `ro.boot.verifiedbootstate=green`. Публичный RSA-ключ есть непосредственно в U-Boot, и установлены два AVB callback сравнения полученного ключа с OEM-ключом. Поэтому замена vbmeta на образ, подписанный сторонним PEM, **не должна рассматриваться как безопасная или гарантированно загрузочная**. Исследование не выполняло записи разделов и не проверяло нестандартные исключения при загрузке.

## Ограничения

Декомпиляция Ghidra приближённая: неопознанные функции названы по адресам, вывод API о возврате функции отдельно от значения `trusted` может быть неоднозначен без структуры callback-таблицы и фактического пути вызовов. Для строгого доказательства выполнения проверки требуется связать `AvbOps` с `avb_slot_verify`, проследить состояние `locked`, `ALLOW_VERIFICATION_ERROR`, rollback и путь отказа.

## Следующий безопасный этап

1. Найти вызов `0xA2628` и то, куда передаётся таблица callbacks.
2. Найти вызов `avb_slot_verify`, проверить флаги и `is_device_unlocked`.
3. Проанализировать пути при несовпадении OEM-ключа и при `VBMETA_VERIFY_RESULT_SIGNATURE_MISMATCH`.
4. Отдельно разобрать загрузку/доверие `mboot`, `optee` и заводского PKG, чтобы не путать раннюю цепочку secure boot и AVB.

Все шаги выше — статические исследования; ничего на реальном проекторе менять не нужно.
