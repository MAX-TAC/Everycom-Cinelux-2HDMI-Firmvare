# CineLux 2-HDMI: варианты исследования защищённого PKG

## Что проверено

- Полный RAR SHA256 `170f745dc1711c2dae6410dd51f0a8bf5bb7c637e11b8dd3e5f59fbea8c388f3`; единственное вложение `upgrade_image.pkg` 1,301,025,152 байта, SHA256 `4abef5d594803d09c20316a7cd52ab623dd7fb1a228472eb0e243d6d750ebb4c`.
- dipcore/mstar-bin-tool отказывается разобрать при переименовании в BIN (`UnicodeDecodeError` при чтении заголовка); openlgtv/epk2extract v4.8 отклоняет формат (`Unsupported input file format`).
- Заголовок содержит высокоэнтропийные первые 256 байт, версию `V_0.0.0` ровно по смещению `0x100`, и строки `# REE_OFFSET_START = 0x1000 #`, `# REE_OFFSET_LEN = 0x4d8c0000 #` с `0x300`. Читаемая область нулей, затем заголовок `MTK.....` на `0x500` и `.....mtk` на `0x578` с бинарной структурой.
- Арифметика точная: `0x1000 + 0x4d8c0000 + 0x180 = 0x4d8c1180` (точный размер PKG). Значит, 4-КиБ обёртка, большая REE-область и 384-байтовый трейлер. Это воспроизводимый результат, а не эвристика Binwalk.
- Содержимое REE при `0x1000` не начинается с обычного gzip/zlib/xz/DEFLATE, Android sparse, ZIP, ELF, SquashFS и известных заголовков. Энтропия ~7.9998 бит/байт в 1-МиБ фрагментах разных участков, файл практически не сжимается RAR. Данные вероятнее всего зашифрованы или упакованы нестандартным плотным способом; алгоритм AES/подписывание RSA пока **не доказаны**.
- Первые 256 байт и последние 384 байта напоминают подписи/криптографические структуры из-за длин и энтропии, но никаких открытых ключей и проверки RSA пока нет — называть их подтверждёнными подписями нельзя.

## Внешние совпадения

- Tecon MT9660 SDK note: платформа `mt9660_cnt-apollo-mp-2101-cnt-mt5873-71-001-2`; `lunch mt5873_cd-userdebug`; сборка `out/target/product/mt5873/images/upgrade_image.pkg`; команда загрузчика `mtkupgrade usb upgrade_image.pkg`. https://bbs.cvbs.cn/forum.php?mod=viewthread&tid=2933
- Тема 4PDA содержит образ XGIMI Horizon 20/RS20 с `V_1.1.55`, `REE_OFFSET_START = 0x1000`, `REE_OFFSET_LEN = 0x958c0000`; следовательно, формат обёртки не специфичен для CineLux. https://4pda.to/forum/index.php?showtopic=847902&st=3500
- Hisense 43A6K: тот же заголовок с `REE_OFFSET_START = 0x1000`, `REE_OFFSET_LEN = 0x32470000`: https://arhiva.elitesecurity.org/t509739-Hisense-firmware-unpack

## Возможные направления (от наиболее практичного)

1. Попросить у фабрики или поставщика MTK SDK `mt5873` / инженерный `system.img`, `vendor.img`, `super.img`, `boot.img` и фирменные pack/unpack tools для `mtkupgrade`; одновременно запросить официальный формат `upgrade_image.pkg`, формат подписей, образ восстановления и тип платы.
2. После получения D11 проверить `adb shell getprop`, `su`, `ls -l /dev/block/by-name`, `mount`, `getprop ro.boot.slot_suffix`, `vendor/etc/vintf/manifest.xml`. При наличии root создать и локально сохранить верифицированные SHA256 дампы **читаемых** разделов. Персональные разделы (persist, nvram, nvdata, TEE, DRM, заводские калибровки) хранить строго приватно.
3. Если root недоступен, обычно доступны для чтения публичные APK и конфигурации `/system`, `/vendor`, `getprop`, `pm path`; есть шанс получить функциональные интерфейсы проекторных сервисов без полного дампа. Разметку и возможность извлечения целого образа проверить отдельно.
4. Если найден инструмент с реализацией `mtkupgrade` для конкретного чипа, исследовать его **пассивно** — не запускать обновление или запись на D11, не предполагать совместимость между двух-HDMI версиями. Может оказаться, что проверка подписи и дешифрование выполняются загрузчиком/TEE с аппаратным ключом.
5. Взять второй PKG той же MTK-платформы (например, другую версию CineLux) и сравнить неизменные поля, первый 4К заголовок, смещения и структуру трейлера. Это поможет описать контейнер, но не приведёт само по себе к вычислению стойкого AES-ключа.
6. Если используются аппаратно защищённые ключи, перебор ключа/повторное шифрование нереалистичны; лучшая цель — чистые разделы Android, а не обязательное раскрытие PKG.

## Вывод

Задача принципиально решаема для анализа и кастомизации системы при получении читаемых Android-разделов. Полученный PKG может оказаться **полным защищённым установочным пакетом**, а не OTA-дельтой, но для перепаковки под этот формат дополнительно потребуются знания о подписи/цепочке доверия. Никаких инструкций по прошивке D11 данным файлом без аппаратной сверки давать нельзя.
