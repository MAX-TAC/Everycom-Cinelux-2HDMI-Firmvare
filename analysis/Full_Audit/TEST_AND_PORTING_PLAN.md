# CineLux / FlixTone D11 custom firmware — проверяемый план совместимости

Пока отсутствуют реальные тесты загрузчика и запись кастомных разделов. Это **план экспериментов**, не подтверждённая совместимость.

## Этап 0 — уже сделано (только чтение двух PKG)

- Восстановлены системные разделы и найдены OEM аппаратные профили `8052` (1 HDMI) и `8054` (2 HDMI).
- Совпадают GPT разметка, открытый ключ AVB SHA256_RSA4096, 207 DTBO-описаний (после перестановки) и почти все базовые скрипты/конфигурации.
- Выявлены изменения в JNI, системном меню, HDMI, моторе фокуса и дополнительной Linux-среде.
- Установлены текущие ограничения: неизвестно, принимает ли загрузчик кастомную подпись PKG, и можно ли разблокировать AVB.

## Этап 1 — безопасная диагностика владельцев через ADB

Команды можно выполнять без root. **Не публиковать ADB-порт в интернет:** доступ к удалённому проектору организовать через личный VPN, отключить отладку после работы.

```bash
adb devices -l
adb shell getprop ro.rjpj.machine.id
adb shell getprop ro.rjpj.yunota.version
adb shell getprop ro.rjpj.yunota.url
adb shell getprop ro.rjpj.hdmi.ports
adb shell getprop ro.rjpj.hdmi.port.count
adb shell getprop ro.rjpj.support.toffunction
adb shell getprop ro.rjpj.autokeystone.poweron
adb shell getprop ro.zeasn.devicetype
adb shell getprop ro.build.fingerprint
adb shell getprop ro.product.cpu.abilist
adb shell getprop ro.zygote
adb shell getprop ro.boot.hardware
adb shell getprop ro.boot.slot_suffix
adb shell getprop ro.boot.verifiedbootstate
adb shell getprop ro.boot.flash.locked
adb shell getprop ro.boot.vbmeta.device_state
adb shell getprop ro.boot.veritymode
adb shell getprop ro.debuggable
adb shell getprop ro.adb.secure
adb shell getenforce
adb shell id
adb shell command -v su
adb shell ls -l /dev/block/by-name
adb shell pm list packages -f
adb shell cmd package resolve-activity -a android.settings.SETTINGS
```

Параметр отсутствует — не равно отключена функция. Информация AIDA64 о root — не полноценная проверка прав `su`/`adb root`.

**Вопросы для владельца:** ревизия платы на наклейке, число HDMI, наличие ToF-камеры и автоматической трапеции, отображаемая версия OTA (экран), последняя дата обновления, работает ли 4K/HDR/eARC/CEC.

## Этап 2 — чистое пользовательское приложение

- Сделать пробную панель `ProjectorControl`, пока без удаления OEM-сервисов. Использовать безопасные публичные/уже проверенные Android действия.
- Проверить наличие `com.android.tv.settings` и `com.trd.framework`, реакцию на стандартные системные Intent.
- По отдельности проверить изменение источников, фокуса, зеркала, трапеции, изображения.
- Нельзя управлять мотором непроверенными командами: ограничить движение, время и иметь автоматическую остановку/страховку.

## Этап 3 — техническая подготовка записи образов

- Определить путь аварийного восстановления **для каждой физической платы**, не только доступность OEM-установщика.
- Выяснить active slot (если A/B), состояние блокировки, реально применяемые AVB и rollback, поддержку fastboot/fastbootd (если документирована).
- До изменения `system`, `boot`, `dtbo`, `vendor`: создать приватные резервные копии заводских уникальных разделов (factory/eeprom/project_id/persist), проверить SHA и способ восстановления.
- Проверять возможности на максимально обратимых изменениях — **не** с помощью полного PKG с `gpt clean`, `wipeuserdata`, `erase eeprom`.

## Этап 4 — общая кодовая база / отдельные аппаратные пакеты

- Общий `system`: настройки Android TV, Projectivy как опция, пользовательский сервис, очистка ненужных приложений.
- Профиль 8052: один HDMI, ToF=0, собственный моторный интерфейс и образы заводской аппаратной части.
- Профиль 8054: два HDMI, ToF=1, I²C JNI и свой моторный интерфейс, отдельные заводские аппаратные данные.
- Одинаковый `trdmiddle` можно использовать как общую основу; фактические API проверить на обоих устройствах.
- По умолчанию выпускаются два установочных артефакта из одной кодовой базы — это **не** двойная разработка.
- Единый PKG с определением ревизии до перезаписи оборудования возможен лишь после подтверждения надёжного аппаратного идентификатора и правил подписи.

## Условия принятия решения о **едином устанавливаемом образе**

Нужны одновременно: аппаратный ID, который нельзя случайно подменить из `build.prop`; однозначный выбор конфигурации DTBO и драйверов; полная совместимость аппаратных служб; возможность установки и загрузки самостоятельно подписанного Android; проверенный откат для обеих ревизий.

Пока неизвестно хотя бы одно из этих условий, **один общий исходный проект + два аппаратных установщика** — технически правильный вариант.
