# Классификация отличий 8052/8054: аппаратные, обновления ПО и пока не объяснённые

**Сравниваем только известные оригиналы:**
- августовский factory PKG 8052 (1 HDMI);
- сентябрьский factory PKG 8054 (2 HDMI);
- октябрьский OTA 8052.1.0.4.
- Для 8054.1.0.4 нет оригинального payload или полного дампа, данные владельца ожидаются.

## Метод установления причины отличия

У нас три измерения: **разная сборка того же устройства во времени**, **разные устройства в одно и то же время**, **разный активный аппаратный компонент на живом железе**.

1. **Перешло в новую 8052 вместе с обновлением?** Если `8052-Aug` ≠ `8054-Sep`, но `8052-Oct` = `8054-Sep`, это **сильный признак общего обновления OEM кода** вместо индивидуального аппаратного изменения. Доказать это без исходников нельзя; результат маркировать `обоснованная гипотеза`.
2. **Отличаются свойства machine.id/порты HDMI/ToF при одинаковом APK?** Это свидетельствует в пользу **конфигурационных аппаратных профилей**, работающих на общей реализации.
3. **Если только SHA изменён, но `.text` тот же**, нельзя утверждать, что изменились выполняемые алгоритмы. Может отличаться `.rodata`, релокация, модинформация, build-id, ABI data.
4. **Если `.text` изменён**, искать изменённую функцию и семантику; зафиксировать конкретные ветви/константы. Отличие драйвера не делает это автоматически «поддержкой 2 HDMI».
5. **Признак багфикса**: новая обработка ошибки, ограничения диапазона, исправленное состояние автомата/таймаут — доказать по телам функций и направлению изменений. По именам методов этого делать нельзя.
6. **Аппаратно-обязательный код**: активная функция подтверждена профилем + реально используется на устройстве + имеет специфичные пути/условия для иной платы. Лишь тогда делать отдельную реализацию/overlay.

## Почему один MT7663 не должен задерживать кастомизацию UI

`wlan_mt7663.ko` — модуль беспроводной связи, НЕ базовый CPU MT9660. Исходный firmware включает драйверы нескольких альтернативных Wi-Fi-чипов (MT7663/MT7902/MT7961). Но наличие `.ko` не доказывает, что установлен модуль или используется конкретный чип. Пока `/proc/modules`, `dmesg` и идентификация адаптера не укажут на активный драйвер, исследование его каждой инструкции **не является блокером удаления zxstore или замены HOME**. Однако сам `vendor` в будущем стоковом кастоме сохраняем неизменённым.

## Чего недостаточно

- Подтвердить дату/входные бинарники 8054.1.0.4 (в руках лишь 8054.1.0.1).
- Выделить реальные отличия в `RuiAutoFocus.startTof` и взаимосвязях API motor/ToF.
- Проверить точное значение `InputSourceID`, отличие гаммы и PMU.
- Сверить отдельно TV Linux `tvservice`, не только Android ELF.
- На реальном железе подтвердить `/proc/modules`, manifest services, HDMI/ToF, настройки кнопок пульта.

## Дальнейшие инженерные правила

Для каждого файла в будущей release manifest фиксировать: baseline `8052`/`8054`, SHA256, профиль/общий, причина необходимости отдельных копий, исходный код/метод, риск удаления, проверка регрессии. **Нельзя** автоматически принимать самую новую версию драйвера из другого профиля только по дате.
