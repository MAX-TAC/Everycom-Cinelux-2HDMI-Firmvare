# Архитектура будущих GitHub OTA каналов для MT9660 Custom

**Статус: схема и пустой каталог без опубликованных обновлений. Ни одного flashable update нет, установщик отсутствует.** Не перенаправлять существующий OEM updater на этот каталог, пока нет подписанной и испытанной OTA.

## Два независимых канала

- **8052: Everycom CineLux 4K**, база RUIOS.8052.1.0.4 (1 HDMI).
- **8054: FlixTone D11 Master**, на данный момент верифицирована только заводская RUIOS.8054.1.0.1 (2 HDMI; не путать с ожидаемой более новой рабочей версией).

Проект общей кодовой базы, но несовместимые low-level boot/DTBO/TVservice и различающиеся hardware IDs. Каждый APK/образ/OTA тестировать на нужной плате. Любой релиз подписывать отдельным ключом проекта, а не рассчитывать на публичные AOSP testkeys.

## Уже установленный штатный формат 8052

Исходный адрес: https://www.szrjyun.com/ota/android/mt9660/8052/8052_ota.json

Подтверждённые поля: ver, url, size, md5, desc1..desc3, forcepush, forceselect, pushstyle, pushinfo1..3, ab_update, ab_offset, ab_size, ab_prop1..ab_prop4. В 8052 ab_update=direct; offset/size соответствуют payload.bin внутри конкретного ZIP. **Нельзя заполнять поля offset, hash или size макетными значениями**: неверные значения могут привести к неработающей/опасной процедуре OTA.

Фактический адрес API для 8054 по известному маршруту на момент аудита отвечал 404: не считать это доказательством отсутствия другого OTA канала.

RuiYunOta и trdservice взаимосвязаны: trdservice обращается к com.rjpj.yunota.OTACheckService. Адрес может оказаться зашитым в Java/ресурсах/props. Перенаправление DNS не использовать: оно небезопасно, затрагивает чужой домен и зависит от TLS. Сначала исследовать код и задокументировать источник конфигурации, তারপর в отдельной сборке менять конкретную точку вызова либо добавлять независимый updater с экраном подтверждения.

## Правильное разделение ролей GitHub

1. GitHub Releases — размещение проверенных установочных OTA архивов соответствующего hardware channel. Стандартные immutable versioned Release asset URLs (не подменять по существующему tag).
2. GitHub Pages (или другой контролируемый HTTPS origin) — статический канал JSON-манифеста: индекс версий и сведений о совместимости. Не подразумевать, что GitHub Releases API имеет такой же формат, как szrjyun JSON.
3. Подписанные метаданные проекта с закреплённым публичным ключом, SHA-256 каждого архива, rollback prevention и реальные OTA signatures; MD5 из старого формата недостаточен для обеспечения доверенной целостности.
4. До загрузки показывать брендинг, модель, исходную/целевую версии, размер, changelog, запрашивать согласие пользователя. Не делать forced update в первой версии.
5. Разрешать скачивание/прошивку **только** если подтверждены board SKU, базовая сборка и схема разделов, AVB trust/bootloader state, подпись OTA, безопасный rollback. Если что-то не совпадает — отказ.
6. Сохранить сервис производителя как резервный источник диагностики/ручного восстановления до проверки собственного OTA. Не объявлять публичный GitHub JSON действующим OTA сервером.

## Что включено в репозиторий

`ota/channels.template.json` — **намеренно пустые каналы** (не публиковать как доступные обновления).
Отдельный проект чтения/проверки этого каталога будет возможен независимо от низкоуровневой установки.

## Для первого релиза

Безопасная ступень 1: "Проверить обновления" показывает доступность нового релиза с проверенным manifest, changelog и ссылкой, но **автоматическую установку не выполняет**. Ступень 2: самостоятельное A/B обновление после реального подтверждения recovery/AVB; нельзя обещать его работоспособность на основании одного JSON или testkey сертификата.
